API Runtime

Runtime Parameters

OctoShaper graphs expose parameters that control node inputs at graph level. At runtime, you can override these parameters through the ProceduralGraphExecutor component or directly on a ProceduralConfiguration. This page covers the complete parameter override API and best practices for driving graphs from gameplay code.

Quick Start

Basic parameter override

Set overrides by parameter name before calling a generate method. Overrides apply to the next generation only and do not mutate the graph asset.

using CuriousTrove.OctoShaper;
using UnityEngine;

public sealed class RuntimeParameterExample : MonoBehaviour
{
    [SerializeField] private ProceduralGraphExecutor executor;

    public void ApplyGameplayState(int count, float width)
    {
        executor.SetParameterOverride("Count", count);
        executor.SetParameterOverride("Width", width);
        executor.GenerateSync();
    }

    public void ResetToDefaults()
    {
        executor.ClearParameterOverrides();
        executor.GenerateSync();
    }
}

Executor-level parameter API

The ProceduralGraphExecutor wraps parameter overrides on its internal ProceduralConfiguration. These methods are the preferred surface for runtime gameplay code.

SetParameterOverride(Guid parameterId, object value)

Overrides a graph parameter by its unique Guid. Use this when you have already cached the parameter id from the graph asset.

SetParameterOverride(string parameterName, object value)

Overrides a graph parameter by its authored name. This is the most common surface for runtime code because parameter names are human-readable and stable across graph edits. The value must be type-compatible with the parameter's declared type.

TrySetParameterOverride(string parameterName, object value)

Same as SetParameterOverride(string, object) but returns false instead of throwing when the parameter name is not found. Use this when you want graceful fallback for optional parameters.

ClearParameterOverrides()

Removes all parameter overrides, restoring the graph's default parameter values for the next generation. The graph asset itself is never modified.

Working with ProceduralConfiguration directly

When using the low-level runtime API (without a ProceduralGraphExecutor component), create a ProceduralConfiguration and set overrides on it directly. Pass it to the executor's ExecuteAsync method.

using System.Threading.Tasks;
using CuriousTrove.OctoShaper;
using CuriousTrove.OctoShaper.Core.Data;
using UnityEngine;

public sealed class DirectParameterExample : MonoBehaviour
{
    [SerializeField] private ProceduralGraph graph;

    public async Task<ElementSet> GenerateWithParameters(int count)
    {
        var configuration = new ProceduralConfiguration();

        // Set overrides before execution.
        configuration.SetParameterOverride(
            graph.Parameters[0].Id,
            count);

        var context = OctoShaperRuntime.CreateExecutionContext(graph);
        var executor = OctoShaperRuntime.CreateExecutor(graph);

        await executor.ExecuteAsync(
            context,
            ElementSet.CreateImplicitSingle(),
            configuration);

        return (ElementSet)context.GetMainOutputValue();
    }
}

Note: The ProceduralConfiguration also exposes TrySetParameter<T>(string, T) which is a generic-typed variant of the string-based override, useful when you want compile-time type checking for the override value.

Configuration-level API (ProceduralConfiguration)

These methods live on ProceduralConfiguration and are used indirectly through the executor. They are also available when you construct a configuration manually.

SetParameterOverride(Guid parameterId, object value)

Sets an override on the configuration by parameter Guid. The executor delegates to this method.

TrySetParameter<T>(string parameterName, T value)

Generic-typed override by name. Returns true if the parameter exists and the type matches; false otherwise. This is the preferred surface for direct configuration manipulation because it validates the type at compile time.

ClearOverrides()

Removes all overrides from the configuration. The executor's ClearParameterOverrides() delegates to this.

Best practices

  • Use name-based overrides for gameplay code. Parameter names are stable across most graph edits, whereas Guid-based ids require caching from the graph asset.
  • Wrap parameter names in constants or a dedicated class. Avoid scattering string literals across your project. A central GraphParameters static class makes refactoring safer.
  • Set overrides before the first generation. Overrides only take effect on the next call to a generate method. Setting them after generation has no immediate effect.
  • Overrides do not mutate the graph asset. The original graph retains its default parameter values. Overrides live only on the configuration/executor.
  • Use TrySetParameterOverride for optional parameters. When a parameter may or may not exist (e.g., different graph versions), the Try variant avoids runtime exceptions.
